## 0. What this lab is (a model, not a real 360 product)

The lab models the **native (.so) layer of 360 jiagu** as a **modified UPX**. This is
historically accurate (early 360 native protection was built on UPX). The unpacking
*mechanism* is identical to real 360 (runtime decompress → jump to OEP → restore code →
ELF Fix); what differs is only the *rewritten feature* — the magic `UPX!` is replaced by
a 4-byte token (`JG!!`), and a plaintext `360 4.24` version string may appear.

Two confirmed markers of the modeling (both real, verified on this machine):

- `src/policy_inc.h` contains `"pol:...."` lines (1000 entries, ~45 KB) — this is the
  compressible bulk that makes UPX profitable. It also embeds
  `360jiagu_lab_payload_marker_v1` via `src/target.c:26`.
- `build/pack.sh` lines 26-27 rewrite the stub's internal version string
  `"UPX 4.24"` → `"360 4.24"` **only if `upx -t` still passes afterwards**; on failure it
  reverts (line 42-48). On this machine the injection **succeeded** (see §6, marker scan).

**DEX-layer hardening is out of scope for this lab.**

> **Why ET_EXEC for the packed samples?** Official UPX 4.2.4 refuses to pack Android
> `ET_DYN` `.so` (`NotCompressibleException`). `pack.sh:22` does
> `printf '\x02\x00' | dd of=_tmp_orig.so bs=1 seek=16 conv=notrunc` — i.e. it flips the
> `e_type` field (offset 16, 2 bytes, LE) to `ET_EXEC(2)`, packs, and leaves it. The
> unpacking mechanism is unchanged; only this 2-byte field differs. This is why the
> verification in §7 ignores exactly offset 16..17.

## 3. `tools/detect_360.py` — the detector, line by line

### 3.1 CLI surface (`__main__`, lines 326–338)

```
python tools/detect_360.py <file...> [--brief] [--verify] [--upx <path>]
```
- `--brief`: print verdict rows only (hide the "判据" explanation line).
- `--verify`: for each magic candidate, patch → `upx -t` to **empirically** confirm which
  token is the real rewritten magic.
- Non-`--` args are treated as files (loop, line 337).

**Note on output encoding:** on Windows the default console codepage mangles the Chinese
labels. Set `PYTHONIOENCODING=utf-8` (Bash `export PYTHONIOENCODING=utf-8`; PowerShell
`$env:PYTHONIOENCODING='utf-8'`). Everything below was run with that set.

### 3.2 ELF parsing (`parse_elf`, lines 101–133)

Pure `struct` reader, **little-endian only** (`en="<"` is hard-coded — a big-endian ELF
would be mis-parsed; acceptable for Android ARM/x86 targets). Reads `e_type`/`e_machine`
@16, `e_entry`/`e_phoff`/`e_shoff` @24, `e_phentsize`/`e_phnum`/`e_shentsize`/`e_shnum`
@54 (ELF64) or @42 (ELF32). Collects only `PT_LOAD`(type==1) entries into `loads` with
`filesz`/`memsz`/`vaddr`/`flags`, and all sections into `sect`.

Returns `None` if the first 4 bytes are not `\x7fELF` → `detect()` prints
`[!] 不是 ELF 文件` and returns `None` (verified: feeding a text file prints exactly that
and exits **0**, not an error code — the non-ELF branch is not a failure exit).

### 3.3 Feature extraction (all in `detect()`, lines 163–233)

Constants you must know:

| symbol | value | line | meaning |
|---|---|---|---|
| `JIAGU_MARKERS` | `(b"360jiagu", b"360 4.24", b"Jiagu")` | 37 | plaintext 360 attribution |
| `JG_TOKEN` | `b"JG!!"` | 39 | rewritten-magic placeholder |
| entropy threshold | `H > 7.0` | 188 (`f2`) | compressed/encrypted body |
| big-buffer | `memsz/filesz ≥ 4` **and** `memsz ≥ 0x8000` (32 KB) | 189-190 (`f3`) | UPX0 decompress target |
| ratio threshold | `ratio_mem ≥ 3.0` | 198 (`f5`) | mem/file inflation |
| `sz_unc` window | `1000 < tail4 < 64 MiB` **and** `tail4 > len(d)` | 200-201 (`f7`) | trailing uncompressed-size |
| magic candidate count | `2 ≤ count ≤ 16` | 145 (`lo=2, hi=16`) | repetitiveness for rewritten magic |
| candidate tail window | last 96 bytes | 135 (`tail=96`) | candidate must appear near EOF |

Feature by feature:

- **F1** `e_shnum == 0` (+2). Packs strip the section header table.
- **F2** whole-file Shannon entropy `> 7.0` (+2). Helper `entropy()` lines 94–99.
- **F3** a `PT_LOAD` with `filesz>0`, `memsz/filesz ≥ 4`, `memsz ≥ 0x8000` exists (+3).
  The `≥32 KB` lower bound is deliberate — without it, a normal `.bss` (in `orig.so`,
  the `memsz=0x1060` segment) would be misread as a UPX buffer. See pitfall §14.4.
- **F4** `e_entry` falls inside a `PT_LOAD` that is **not** `loads[0]` (+2). Uses
  `vaddr ≤ e_entry < vaddr+memsz` (line 194). Note: **if `e_entry` is not in any load,
  `stub` is `None` and the row prints "未落在任何 PT_LOAD" but F4 is simply not hit.**
- **F5** `total_memsz/len(d) ≥ 3.0` (+2).
- **F6** `d.count(b"UPX!") > 0` (+3).
- **F7** `tail4 = struct.unpack_from("<I", d, len(d)-12)` — the 4-byte LE word at **EOF-12**
  — is in `(1000, 64 MiB)` **and** larger than the file (+2). Verified real values:
  `libtarget_360.so` tail4 = `0xAB70` = **43888** (== the original size); `libtarget_orig.so`
  tail4 = 0. This is the UPX trailer's uncompressed-size field.
- **F8** `(not f6) and packed_ev >= 2 and len(cands) > 0` (+3), where
  `packed_ev = sum([f1,f2,f3,f4,f5])`.

### 3.4 Magic candidates (`magic_candidates`, lines 135–160)

Enumerate every 4-byte window; keep those that (a) are not `UPX!`, (b) occur
`2..16` times, (c) are not 4 identical bytes of `00`/`FF`, (d) appear in the last 96
bytes. Sort with printable-ASCII tokens first, then by occurrence count; return top 5.

Verified candidate list for the variant sample (offsets are real):

```
token b'JG!!'         x4  @ ['0x98', '0x3cfb', '0x45cf', '0x45d8']
token b'\x00\x00p\xab' x2 @ ['0xa2', '0x45ee']
token b'\x00p\xab\x00' x2 @ ['0xa3', '0x45ef']
token b'\x00\x00\x00\t' x2 @ ['0x3640', '0x45c6']
token b'\x00\x00\t\xff' x2 @ ['0x3641', '0x45c7']
```

The last four are **coincidental** (`\x00\x00p\xab` etc.). This is why static candidates
alone are insufficient, and why `--verify` exists.

### 3.5 B13 (lines 205–209) — the ELF-structure anomaly signal

```python
exec_load = any((s.get("flags", 0) & 1) for s in e["loads"])
b13 = (e["e_type"] == 3 and e["e_shnum"] == 0 and exec_load)
```
**All three conditions are required.** Normal NDK `.so` always carries complete sections,
so B13 never fires on them. Proven gating I ran (§6): stripping the *packed* (`ET_EXEC`)
sample does **not** raise B13 (its `e_type==2` fails the first clause) — but note the
verdict then still reads "标准 360 加固" because the F-scoring is independent. B13 is
reported as **"疑似"** and is only allowed to *pre-empt the fallback* verdict (line 283),
never to upgrade a scored-up shell verdict.

### 3.6 Verdict logic (lines 258–289) — exact decision order

```
if   f6 and score>=6:  → 标准 360 加固 / 标准 UPX 壳 (name by jiagu_marker or jg_token_hits)
elif f8 and score>=6:  → ★ 变种 360 加固 / ★ 变种 UPX/未知壳
elif score>=4:         → 疑似加壳（非 360 或深度魔改）
else:                  → 未见已知加固特征（≠未加壳）;  if b13 → 疑似 SO 加壳/自实现 Linker
```
Note the **early-out**: `b13` does NOT override a scored verdict. The `packed` flag is
True in every branch except the final non-B13 fallback; `b13` is returned separately in
the result dict, which is what `check_so_samples.py` asserts on.

Returns `dict(b13, verdict, score, e_type, e_shnum, is_packed)`.

## 5. Toolchain resolution — `build/locate.sh` (4 tiers)

Precedence for every tool: **CLI arg > env var > project config > auto-detect**.

- **python** (`find_python`, 48–55): `$PYTHON` → `python` → `python3` → `py`.
- **SDK** (`find_sdk`, 58–77): `$ANDROID_HOME` → `$ANDROID_SDK_ROOT` → `$ANDROID_USER_HOME`
  (must contain `platforms/`) → derive from `aapt2`/`adb` on PATH → common paths.
- **NDK** (`find_ndk`, 80–91): `$ANDROID_NDK_HOME` / `$NDK_ROOT` / `$ANDROID_NDK_ROOT`
  → newest `<SDK>/ndk/*` containing `toolchains/llvm/prebuilt/windows-x86_64/bin/clang`.
- **UPX** (`find_upx`, 97–109): `$UPX` → **`$ROOT/upx.exe`** → PATH → `tools/upx396.exe`.

**UPX ordering is project-internal-first on purpose**: the lab's measured numbers were
produced with the bundled 4.2.4. To switch versions, set `UPX=<path>` explicitly — do not
rely on PATH silently swapping in another UPX.

## 6. Marker scan — the "360 attribution" is two independent routes

I scanned every sample for the four relevant substrings (raw byte `grep -a -c`):

| sample | `360jiagu` | `360 4.24` | `UPX 4.24` | `Jiagu` |
|---|---|---|---|---|
| orig | **1** | 0 | 0 | **1** |
| 360 standard | 0 | **1** | 0 | 0 |
| 360 variant | 0 | **1** | 0 | 0 |
| stripped | **1** | 0 | 0 | **1** |
| orig_arm64 | **1** | 0 | 0 | **1** |

Reading:
- `orig.so` matches `360jiagu`/`Jiagu` because the **payload itself** contains the marker
  string `360jiagu_lab_payload_marker_v1` and the SECRET/FLAG anchors (`src/target.c:21-26`).
  → **the 360 attribution marker is present even on the clean sample.**
- The *packed* samples lost those strings (they are inside the compressed payload); they
  instead carry the stub's `360 4.24` version string.
- **Therefore `jiagu_marker` is NOT a reliable discriminator of "is this 360".** In fact,
  in the standard-360 verdict path, the naming branch `if jiagu_marker or jg_token_hits>0`
  (line 261) is satisfied by the injected `360 4.24` alone. It's cosmetic (naming only) —
  never feeds scoring. Do not treat it as evidence of packing.

`360 4.24` sits at file offset **0x37da** in the packed samples, inside the stub region,
in the context `...backer http://upx.sf.net $\n\x00$Id: 360 4.24 Copyright (C) 1996-2024...`.
The magic `UPX!` appears at offset `0x98` (stub header) among the 4 occurrences.

## 7. `tools/solve_360.py` — solution A (repair magic → `upx -d` → verify)

### 7.1 CLI
```
python tools/solve_360.py <src.so> <out.so> [--orig <orig.so>] [--token XXXX]
                          [--upx PATH] [--anchor S]... [--anchors-file PATH]
```
Positional: `pos[0]`=src, `pos[1]`=out, `pos[2]`=orig if not given via `--orig`.

### 7.2 Internals
- `find_upx` (57–72): same 4-tier order as detect (`--upx` > `$UPX` > project root >
  PATH > `tools/upx396.exe`).
- `_upx_from_path` (38–55): manual PATH walk that **skips the CWD** — because
  `shutil.which()` on Windows searches CWD first and would let the project's own `upx.exe`
  shadow a system one unexpectedly.
- `load_anchors` (74–92): explicit `--anchor`/`--anchors-file` if given, else read
  `<tools>/anchors.txt` (comments `#`, blank lines skipped); empty → anchor check skipped.
- `candidates` (101–111): all 4-byte windows ≠`UPX!` occurring `≥2` times, sorted with
  tail-residents first then by count; limit 60. (Different from detect's `2..16`/tail-96;
  solve relies on the subsequent `upx -t` to prune, so it casts a wider net.)
- `solve` (113–180): patch each candidate → `upx -t` (temp `%TEMP%/_solve_probe.so`); first
  OK wins; `upx -d repaired -o out`; then anchor check; then if `--orig` given, compare
  sizes and print diff count **ignoring offsets 16..17** (line 175) — this is the single
  `e_type` byte.

### 7.3 THE PITFALL — a standard 360 sample makes solve report failure

I ran solve on **both** samples. The standard sample **FAILS**, and the failure message is
misleading:

```
$ python tools/solve_360.py samples/so/libtarget_360.so out.so --orig samples/so/libtarget_orig.so
[*] 样本: samples/so/libtarget_360.so (17916 bytes)
[*] 现有 'UPX!' 数量: 4
[*] 使用的 upx: upx.exe
[!] 未能通过特征修复使 upx -t 通过 -> 该变种改了 Stub/校验，需走内存 dump 路线
```

**Root cause (read the code, don't trust the message):** line 127
`if data.count(MAGIC) == 0: tried += candidates(...)`. When the magic is already `UPX!`,
there is **nothing to try** — the candidate list stays empty, the loop body never runs,
`found` stays `None`, and it falls into the generic "须走内存 dump" branch. The advice is
wrong for this input: the standard sample is already unpackable by `upx -d` directly.

**Correct moves for a standard sample:**
- Direct: `upx.exe --force-overwrite -d samples/so/libtarget_360.so -o out.so` (verified:
  produces 43888 bytes, differs from golden only at offset 16 = `e_type`).
- Or force solve through the same path with `--token UPX!`:
  ```
  $ python tools/solve_360.py samples/so/libtarget_360.so out.so \
        --orig samples/so/libtarget_orig.so --token UPX!
      候选 token b'UPX!' x4 -> upx -t OK
  [+] 确定被篡改的 token: b'UPX!' -> 还原为 'UPX!'（共 4 处）
  [+] 解包成功: out.so (43888 bytes)
  ... 除 e_type 外差异字节数: 0  => 内容一致，脱壳成功
  ```
- **Which sample solve is *designed* for:** the variant. `detect_360.py` verdicts tell you
  which route: "标准" → `upx -d` directly; "★ 变种" → solve.

### 7.5 MUST CHANGE ALL 4 OCCURRENCES (empirically proven)

## 8. Solution B — `simulate_dump.py` + `dump_fix.py`

### 8.1 `simulate_dump.py`
`parse_segs` (12–43) reads `PT_LOAD`s (32/64-bit, LE). `__main__` maps each `PT_LOAD` into
a flat image of size `max(vaddr+memsz) - min(vaddr)`, copying `filesz` bytes and zero-filling
the `memsz` tail. This is the no-device stand-in for a real process memory dump.

Verified:
```
$ python tools/simulate_dump.py samples/so/libtarget_orig.so analysis_output/sim_dump.bin
[+] simulated dump -> analysis_output/sim_dump.bin  base=0x0 size=53408 (from 4 PT_LOAD, 32-bit)
$ python tools/simulate_dump.py samples/so/libtarget_360.so analysis_output/sim_dump_packed.bin
[+] simulated dump -> analysis_output/sim_dump_packed.bin  base=0x0 size=73890 (from 2 PT_LOAD, 32-bit)
```

### 8.2 `dump_fix.py` — rebuild a loadable ELF from a raw dump
CLI (68–78): `python tools/dump_fix.py <dump.bin> <base_hex> <out.so> [--arch arm|arm64] [--entry-rva HEX]`.

What `build()` (13–66) writes:
- ELF header (52 bytes for arm32, 64 for arm64), `e_type=3` (ET_DYN), `e_machine=0x28`
  (ARM) or `0xb7` (AARCH64), `e_entry = base + entry_rva`.
- **One** `PT_LOAD` (`phnum=1`), flags=7 (RWX), `offset=0x1000` (page-aligned),
  `vaddr=paddr=base`, `filesz=memsz=len(dump)`, align=0x1000.
- Layout: `[ehdr][phdr]` → pad to `0x1000` → dump bytes → 3 section headers (NULL,
  `.text` PROGBITS flags 0x6, `.shstrtab` STRTAB flags 0x2) → names `\x00.text\x00.shstrtab\x00`.
- Helpers `sh32`/`sh64` (47–53) pack the section header entries.

Verified:
```
$ python tools/dump_fix.py analysis_output/sim_dump.bin 0x0 analysis_output/dump_fixed.so --arch arm
[+] wrote analysis_output/dump_fixed.so: base=0x0 size=53408 arch=arm entry=0x0
$ python tools/elf_scan.py analysis_output/dump_fixed.so
FILE: analysis_output/dump_fixed.so (57641 bytes)
  e_type   : 3 (ET_DYN)   e_machine: 0x28 (ARM)   e_entry: 0x0
  [ 0] PT_LOAD      off=0x1000 vaddr=0x0 filesz=0xD0A0 memsz=0xD0A0 flags=7
  [ 1] .text            type=0x1 addr=0x0 off=0x1000 size=0xD0A0
  [ 2] .shstrtab        type=0x3 addr=0x0 off=0xE118 size=0x11
```

**Honest boundary:** `dump_fix.py` is a *minimal* rebuild — single RWX `PT_LOAD` + `.text`,
**no `.dynamic`/`.dynsym`/relocations** (see its own docstring line 310 in SCRIPT.md). It
loads in a disassembler for reading code, but is **not a runnable library**. Real
anti-forensics needs `elf-dump-fix` / manual `.dynamic` reconstruction.

**Anchor subtlety (evidence that the dump is a runtime image):** in `dump_fixed.so`,
`360jiagu`/`JiaguLab`/`getFlag`/`JNI_OnLoad` are findable, but `check_license` and
`blob_selfcheck` are **not** — those two strings live only in the static `.strtab` symbol
table, which is not part of any `PT_LOAD`, so it is absent from a runtime memory image.
That absence is itself proof the flat image represents runtime state.

Verified key contrasts:

## 12. Interface contract with `unpacker/` (who loads whose modules, by path)

`unpacker/labs.py` is a **read-only bridge** (its docstring forbids modifying any lab):
- `_load(module_name, rel_path)` (49-66) loads lab modules **by file path** via
  `importlib.util.spec_from_file_location` — not by package import — because multiple labs
  have same-named files (`reset_lab.py` in all three). Before exec it injects the lab's
  `tools/` dir into `sys.path` so sibling imports resolve.
- 360jiagu entry points: `load_360_detect()` → `360jiagu/tools/detect_360.py`;
  `load_360_solve()` → `360jiagu/tools/solve_360.py`.
- **Exact contract this lab must honor:**
  - `detect_360.detect(path, brief=False, verify=False, upx=None) -> dict` with keys
    `verdict, score, b13, is_packed, e_type, e_shnum`. `analyzer.analyze_so` calls it with
    `brief=True, verify=False` and reads `.verdict/.score/.b13/.is_packed`.
  - `solve_360.solve(src, out, orig=None, token=None, upx_path=None, anchors=()) -> bool`
    and `solve_360.load_anchors(explicit, anchor_file)`.
- `unpacker/unpack.py:98-110` `unpack_so_variant` calls
  `solve.solve(path, out, orig=orig, token=None, upx_path=upx, anchors=anchors)` where
  `anchors` come from `360jiagu/tools/anchors.txt`. **Critical detail (unpack.py:104):**
  it passes `upx_path` explicitly because setting the `UPX` env var makes UPX 5.2.1 parse
  it as an option string and error out.
- The bridge **never calls** `reset_lab.py` (to avoid mutating lab state).

**Consequences for you:** if you rename `detect`/`solve`, change their signatures, or move
`anchors.txt`, you break the bridge and `unpacker/regression.py`. Keep those four names
stable.

## 13. File-format layer details (byte offsets you will need)

- **ELF header field offsets** (LE): `e_type` @16(2), `e_machine` @18(2), `e_entry` @24
  (4/8), `e_phoff` @28(32)/@32(64), `e_shoff` @32(32)/@40(64), `e_phnum` @44(32)/@56(64),
  `e_shnum` @48(32)/@60(64), `e_shstrndx` @50(32)/@62(64).
- **`e_type` values:** 2=ET_EXEC, 3=ET_DYN. `make_stripped_so.py` (20-31) zeroes
  `e_shoff`/`e_shnum`/`e_shstrndx` — ELF64: bytes `[40:48]` and `[60:64]`; ELF32:
  `[32:36]` and `[48:52]`.
- **UPX trailer `sz_unc`:** 4-byte LE word at **EOF-12**. Packed samples read `0xAB70`
  (=43888, the original size); clean sample reads 0.
- **Packed sample PT_LOADs** (from elf_scan): `[0] off=0 filesz=0x1000 memsz=0xD0A0
  flags=6` (RW decompress buffer), `[1] off=0 vaddr=0xE000 filesz=memsz=0x40A2 flags=5`
  (RX stub, contains `e_entry`). Note both have `off=0` — the stub's `off` is a UPX
  artifact; do not assume `off` is monotonic.
- **The 4 `JG!!` offsets:** `0x98`, `0x3cfb`, `0x45cf`, `0x45d8`.
- **Anchor list (`tools/anchors.txt`, 8 entries):** `360jiagu_lab_payload_marker_v1`,
  `JiaguLab-2026-SECRET-KEY`, `flag{jiagu_unpacking_is_fun}`, `com/aegis/NativeLib`,
  `getFlag`, `JNI_OnLoad`, `check_license`, `blob_selfcheck`.

## 14. Sample provenance — where the binaries actually come from

`build/build_android.sh`:
1. `source build/locate.sh`, `locate_require NDK PY`.
2. `python build/gen_policy.py` → writes `src/policy_inc.h` (1000 lines of `"pol:%04d:..."`,

3. arm32: `$CLANG --target=armv7a-linux-androideabi21 -shared -fPIC -O2

   — the `--hash-style=sysv --pack-dyn-relocs=none` flags suppress NDK r27's RELR/GNU-hash
   so the UPX-based shell stays identifiable.
4. arm64: `$CLANG --target=aarch64-linux-android21 ... -o samples/so/libtarget_orig_arm64.so`
   (reference only — UPX 4.2.4 won't pack ET_DYN anyway).

`build/pack.sh`:

2. `upx --force-overwrite -o samples/so/libtarget_360.so _tmp_orig.so` (43888→17916, 40.82%).

5. `make_stripped_so.py` orig → stripped (B13 positive).

`src/target.c` design points relevant to unpacking: `PAYLOAD_MARKER` is a **char array**

(`getFlag`, `checkLicense`, `selfCheck`) — the call chain a re-analyzer should expect at OEP.

## 15. Pitfalls (root-cause, not symptom)

1. **solve on a standard sample reports "须走内存 dump" — false alarm.**
   Root: `solve_360.py:127` only builds candidates when `count("UPX!")==0`. Already-`UPX!`
   input has nothing to patch → `found=None` → generic failure text. Fix: use `upx -d`
   directly, or pass `--token UPX!`. (§7.3)
2. **Changing one magic occurrence fails `upx -t`.** Root: UPX `l_info` checksum covers the
   whole file; must revert **all 4** `JG!!`. Proven with a single-patch test → `NotPackedException`.
   (§7.5)
3. **`upx` picks the wrong copy on Windows.** `shutil.which()` searches CWD first, so the
   project `upx.exe` can shadow a system one. `_upx_from_path` deliberately skips CWD; and
   PATH is *last* in `find_upx` because lab numbers assume the bundled 4.2.4.
4. **`F3` without a size floor misreads `.bss`.** `memsz/filesz≥4` alone flags normal
   zero-fill segments; the `memsz≥0x8000` guard (32 KB) excludes them. (§3.3)
5. **Static magic candidates contain coincidences.** e.g. `\x00\x00p\xab` x2 is random
   data that happens to repeat in the trailer. Never act on candidates without `--verify`.
6. **`UPX!` exclusion logic is intentionally narrow.** `magic_candidates` skips only
   all-`00`/all-`FF` 4-byte runs (line 147) — a real 4-identical-byte token would still be
   considered. Do not tighten this without a sample that requires it.
7. **Tail `sz_unc` is one feature, not proof.** F7 is only +2 and needs `tail4>len(d)` **and**
   a 1000..64 MiB window; a random file could coincidentally satisfy it. Always corroborate.
8. **`e_type` byte genuinely differs after unpack (DYN↔EXEC).** Any byte-compare must
   ignore offset 16..17 — `solve_360.py:175` and `unpacker/unpack.py:75` both do.
9. **Chinese output garbled in Windows console.** Set `PYTHONIOENCODING=utf-8` (or
   `$env:PYTHONIOENCODING='utf-8'` in PowerShell). Python's own locale encoding is the cause;
   this is not a bug in the scripts.
10. **`e_entry` not inside any PT_LOAD → F4 silently misses.** The `stub` variable is
    `None`, F4 prints "未落在任何 PT_LOAD", and the feature is simply not scored — it does
    **not** error. (§3.3)
11. **`upx.exe` / `upx396.exe` are gitignored.** A fresh clone has no UPX; `pack.sh` and
    `--verify` need one. Provide it via `UPX=` or place `upx.exe` at the lab root.
12. **B13 does not override a scored verdict.** Stripping the *packed* sample's headers
    leaves its verdict at "标准 360 加固" (its `e_type==2` fails B13's first clause). B13
    only pre-empts the *fallback* branch. (§3.5, §3.6)
